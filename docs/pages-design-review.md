# Pages・収集システムの設計原則（PR #2094）

実装履歴・容量比較・CI実行記録は [PR #2094](https://github.com/tarematsu/HP/pull/2094) を正本とする。この文書には変更のたびに更新が必要なコミット番号・ファイルサイズ・完了チェックリストを重複掲載しない。

## データ経路と責務

1. **収集**: Stationheadなどのsourceごとに、認証・周期・外部API仕様・収集可否を扱う。Buddiesの収集を優先し、Ohisamaは競合時に遅延・再試行する。Nogizakaの公式ニュース起点の収集は別のトリガーとして維持する。
2. **正規化・保存**: source固有の入力を共通のtrack identity・playback・checkpoint契約へ寄せる。原データの永続化、キュー通知、read modelの生成を同一関数へ過度に詰め込まない。
3. **Worker read model**: 更新通知（revision/Queue）を主経路として変更されたモデルだけ生成し、定期Cronは取りこぼしの回復を担当する。履歴集計では集約済みテーブルを優先し、公開APIの読み込み時にD1へ書き戻さない。
4. **R2公開**: 原則 `pages-response/v1/<model>.json` の1モデル1オブジェクト。共通writer/read contractを使用し、sourceごとに同形の独自envelopeを増やさない。障害時フォールバックも通常公開と同じ保存形式を利用する。
5. **Pages**: `PAGES_READ_MODEL_SERVICE` 経由で公開モデルを読み、source adapterで表示用データを正規化する。APIルートやブラウザ表示層へ収集・集計の責務を持ち込まない。R2の欠損・破損は空の正常データと区別する。

## 共通化すべきものと残すべき差分

- 共通化: source識別、snapshot/queueの正規化、再生トラックの同一性、likes、health/checkpoint、read modelの保存・読み込み、ブラウザの表・グラフ・取得制御。
- source固有: 認証方式、DB binding、スケジュール/優先度、公式ニュース解析、公開可能な表示機能、必要なSQL差分。
- 互換処理: 旧 `actions-v2` は移行読み取りに限定する。通常のwriterへ逆流させず、削除前に本番移行状況を確認する。
- フォールバック: 欠損時の可用性確保に必要な最小限の処理として残す。通常経路の集計を丸ごと二重実装せず、共通の保存形式と再収束経路を使用する。

## コストと正確性

- 無変更時はD1の大量読み込み、D1/R2への書き込み、Queue通知、非表示ブラウザ画面の再取得を発生させない。
- 収集周期を無条件に短縮しない。Buddies優先を維持し、Ohisama/Nogizakaの正常性も確認する。
- 5分収集間の曲遷移・順序逆転・同一通知の再配信・日付境界・古い応答による画面上書きをテストする。
- read modelの欠損を「成功・空データ」として返さず、復旧可能なエラーとして扱う。
- ブラウザ容量は初期JS/CSSと遅延ロード分を分けて測り、実転送量とビルド生成物サイズを混同しない。

## 継続監査

変更後は収集/保存の単体・統合テスト、Pages API契約、PC/スマホの実データと空データ表示、CSV、関連Worker dry-run、通常CIを検証する。CI通過は本番のデータ鮮度・欠損なしを保証しないため、公開R2の更新時刻と収集checkpointを別々に確認する。
